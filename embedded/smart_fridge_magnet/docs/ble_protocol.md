# Smart Fridge Magnet — BLE 命令协议

本文档描述设备端 BLE GATT 命令协议。协议帧格式、公开 UUID 与文件传输命令序列
均**沿用 FrameFilm 上游基线（`562f330`）**，本项目只做「加固 + 规范化 + 补齐配网/
状态查询命令」，不重构帧格式、不改动任何既有 opcode 的取值与语义。

> 实现见 `components/film_service/src/service_ble.c` 与
> `components/film_service/src/service_ble_parser.c`。

---

## 1. 帧格式（与上游一致，未改）

所有命令与响应共用同一帧格式：

```
+--------+--------+--------+------------------+----------+
| HEAD   | CH     | LEN    | DATA (LEN bytes) | CHECKSUM |
| 0x55   | opcode | 数据长 | 载荷              | 和校验    |
+--------+--------+--------+------------------+----------+
偏移: [0]      [1]      [2]      [3 .. 3+LEN-1]     [3+LEN]
整帧长度 = LEN + 4
```

- `HEAD` 固定为 `0x55`。
- `CH` 为通道/操作码（opcode）。
- `LEN` 为单字节数据长度（0–255）。
- `CHECKSUM` 为其前所有字节（HEAD..DATA）的 8 位累加和。
- **接收方在访问任何字段前**先校验：最小长度、`HEAD`、`LEN + 4 == 整帧长度`、
  校验和（先校验后访问）。非法帧一律拒绝且不改变既有状态、不越界、不 panic。
- **发送方**用统一的帧构造器序列化响应，Notify 长度恒等于真实载荷长度，绝不外发
  未初始化填充字节。

## 2. 文件传输命令序列（FILE_*，与上游一致，未改）

严格顺序状态机；乱序命令被拒绝且不打断进行中的传输。BLE 仅作为传输
适配器，经统一文件事务写文件，不自实现保存、校验或上屏。

| opcode | 命令 | 说明 |
| --- | --- | --- |
| `0x03` | FILE_START | 开始一次文件传输 |
| `0x00` | FILE_NAME | 目标文件名（安全基础名，禁路径穿越） |
| `0x01` | FILE_LEN | 声明文件总长（4 字节，大端）；智能冰箱贴屏幕必须 == 209120 |
| `0x02` | FILE_DATA | 分片数据；累计不得超过声明长度 |
| `0x04` | FILE_STOP | 结束传输；核对声明长度与实际接收长度，Notify 成功/失败 |

序列：`FILE_START → FILE_NAME → FILE_LEN → FILE_DATA(×N) → FILE_STOP`。连接断开会
中止未完成的传输（清理临时文件、释放写所有权），当前画面保持不变。

文件管理：`0x05` 删除、`0x06` 列表、`0x07` 显示指定 id、`0x08` 查询当前显示 id。
OTA：`0x10`–`0x13`（第一版保持不动）。

## 3. 设备控制命令（0x20–0x2B，与上游一致）

| opcode | 命令 | 载荷 |
| --- | --- | --- |
| `0x20` / `0x21` | 播放模式 设置 / 查询 | 1 字节（0 手动 / 1 本地 / 2 网络） |
| `0x22` | 恢复出厂并重启 | 无 |
| `0x23` | 读取电量 | 响应 1 字节百分比 |
| `0x24` | 重启 | 无 |
| `0x25` / `0x26` | 休眠开关 设置 / 查询 | 1 字节 0/1 |
| `0x27` / `0x28` | 定时唤醒开关 设置 / 查询 | 1 字节 0/1 |
| `0x29` / `0x2A` | 定时唤醒时间 设置 / 查询 | 2 字节分钟（大端） |
| `0x2B` | SD 卡格式化（已禁用） | 始终返回失败；必须通过本地维护流程操作 |

> ⚠️ **`0x27`–`0x2A` 只在「未配网」时还起作用。** 它们写的是上游的
> `sleep.sleep_auto` / `sleep.sleep_time`，而 `monitor_arm_deep_sleep_wakeup()` 只在
> **设备未配网**时才走这对参数。已配网的设备按
> 「唤醒时间表（`0x48`）→ 兜底周期 → 轮询周期（`0x4A`）」决定唤醒时机，
> 改 `0x29` 不会有任何效果（也不会报错，这正是容易踩的地方）。
> 要控制已配网设备的唤醒时机，用 §4.11 的 `0x48`–`0x4B`。
>
> `0x25`/`0x26`（休眠开关）不受此影响，两种情况下都生效。

## 4. Wi-Fi 网络 / 配网 / 状态查询（0x30–0x43）

规范化说明：`0x30–0x3D` 为上游既有网络命令，取值与语义**保持不变**；
本项目将其配网写入统一收敛到**参数服务**持久化（敏感字段由参数服务在落盘时经
`SFM_BLE_KEY` **at-rest 加密**），并**从 0x3E 起追加**此前不可达的配网字段
（`manifest_url`/`device_id`/`device_token`）与一个合并状态查询命令。

### 4.1 既有网络命令（0x30–0x3D，取值未改）

| opcode | 命令 | 载荷 / 说明 |
| --- | --- | --- |
| `0x30` / `0x31` | Wi-Fi 开关 设置 / 查询 | 1 字节 0/1 |
| `0x32` | 设置 SSID | UTF-8 字节串（1–32）；经参数服务持久化 |
| `0x33` | 查询 SSID | 响应 SSID 字符串（非机密） |
| `0x34` | **设置 Wi-Fi 密码** | 明文字节串（0–63，空串表示开放网络并清除旧密码）；**落盘加密**；不记录明文 |
| `0x35` | **查询 Wi-Fi 密码** | **不再返回明文**，见 §4.3 |
| `0x36` / `0x37` | ~~兼容上游 HTTP film API URL 设置 / 查询~~ **已停用**，见 §4.13 | 设置被忽略；查询恒返回空串 |
| `0x38` / `0x39` | 连接 / 断开 Wi-Fi | 无 |
| `0x3A` | 查询 Wi-Fi 连接状态 | 响应 1 字节 0/1 |
| `0x3B` | 清除网络配置 | 无 |
| `0x3C` | 立即取图 —— 现为 `0x44` SYNC_NOW 的**兼容别名**，见 §4.13 | 无 |
| `0x3D` | 查询取图状态 | 响应 2 字节（状态+进度）；语义见 §4.13 |

### 4.2 新增配网命令（0x3E 起）

| opcode | 命令 | 载荷 / 说明 |
| --- | --- | --- |
| `0x3E` | 设置 `manifest_url` | 字符串（≤127）；非机密；经参数服务持久化 |
| `0x3F` | 查询 `manifest_url` | 响应字符串（非机密） |
| `0x40` | 设置 `device_id` | 字符串（≤47）；非机密；经参数服务持久化 |
| `0x41` | 查询 `device_id` | 响应字符串（非机密） |
| `0x42` | **设置 `device_token`** | 明文字节串（≤127）；**落盘加密**；不记录明文；**无读回命令** |
| `0x43` | 合并状态查询 | 见 §4.4；响应**不含任何机密明文** |

配网字段的完整集合：`SSID`(0x32) / `Wi-Fi 密码`(0x34) / `manifest_url`(0x3E) /
`device_id`(0x40) / `device_token`(0x42)。所有 set 命令都做有界长度校验，并把
（非 NUL 结尾的）BLE 载荷落成有界 NUL 结尾字符串后再交参数服务 setter；密码/令牌
的本地明文副本用后即抹除。

> ⚠️ **发送侧务必用 UTF-8 编码器，不要用 ASCII 编码器。** 上表写的就是 UTF-8，但 Android
> 侧曾用 `String.toByteArray(Charsets.US_ASCII)` 发 SSID —— 那个 API 对无法表示的字符
> **静默替换成 `?`(0x3F)** 而不抛异常。于是中文 SSID「蛮王拉稀丶」变成 5 个问号，固件拿着
> 那串字节去连，永远扫不到 AP（`reason=201 NO_AP_FOUND`）。
>
> 这个 bug 极难自证：App 侧一路成功、固件也不报错，串口把 5 个 `0x3F` 打成 `?????`，
> 恰好和「终端显示不了中文」长得一样，排查方向会被带到密码、5GHz、信号强度上去 ——
> 而网页调试工具用的是 `TextEncoder()`（UTF-8），同一个 AP 一次就连上。
> 中文 SSID 在家用路由器上很常见（手机热点默认名常带中文或 emoji）。
>
> `manifest_url` / `device_id` / `device_token` 与文件名确实**只接受可打印 ASCII**，但
> 遇到非 ASCII 时发送侧应当**显式拒绝**而不是静默替换：`device_id` 变成 `???` 会让
> manifest 请求打到一个不存在的路径并回 404，而 App 侧显示成功。
>
> 长度同理要在**发送侧**拦住。固件对这几个字段一律 `strncpy(dst, src, MAX - 1)`，截断后的
> `device_token` 与「后端根本没登记这个 token」的表现完全一样（都是 401），日志里也长得一样。

> 说明：受单字节 `LEN` 帧限制，配网采用「按字段逐条 set」而非单帧携带全部字段；
> 这与「一条 0x30+ 配网命令」的设计意图等价，且不破坏任何既有 opcode。

### 4.3 禁止读回机密

- **Wi-Fi 密码查询（`0x35`）**：**绝不返回密码明文**。为兼容既有 App 的「有响应」
  契约，仅返回 **1 字节 set/unset 状态位**（`1`=已配置密码，`0`=未配置），App 可据此
  判断是否已配网，但无法取得密码值。
- **`device_token`**：**没有**任何读回 opcode（本项目也未新增），因此令牌**只写不可读**。
- 密码/令牌的明文既不经 BLE 读回，也不写入串口日志。

### 4.4 状态查询响应载荷（`0x43`）

响应帧的 `DATA` 布局（全部为**非机密**字段）：

| 偏移 | 长度 | 字段 | 来源 |
| --- | --- | --- | --- |
| 0 | 1 | Wi-Fi 连接状态 0/1 | `service_wifi_get_connect_status()` |
| 1 | 4 | 最近应用版本（大端 uint32） | `sync.last_applied_version` |
| 5 | 1 | busy 0/1 | 文件事务 `FT_RECEIVING`/`FT_VALIDATING` |
| 6 | 1 | 电量百分比 0–100 | `hal_bat_get_percent()`（钳制） |
| 7 | 1 | 错误串长度 `err_len`（0=无） | — |
| 8 | `err_len` | 最近同步错误（非机密文本，无 NUL） | `sync.last_sync_error` |
| `8 + err_len` | 1 | 休眠模式 0/1 | `sleep.sleep_mode` |

`DATA` 总长 = `9 + err_len`。新增休眠位追加在旧字段之后；旧 App 可忽略尾随字节，
新 App 连接未追加该字节的旧固件时将休眠状态视为未知。响应中**不含** `wifi_password` / `device_token`。
`last_sync_error` 仅承载非机密错误文本；机密由日志脱敏与静态加密路径保护。

### 4.5 SYNC_NOW 立即同步（`0x44`）

| opcode | 命令 | 载荷 / 说明 |
| --- | --- | --- |
| `0x44` | SYNC_NOW 立即触发一次 Wi-Fi 同步检查 | 请求无载荷；响应 1 字节受理状态位（`1`=已受理并触发） |

- 收到 `0x44` 后，设备端立即触发一次**一次性** Wi-Fi manifest 检查
  （意图为 connect → SNTP → manifest），演示时无需等待轮询周期即可拉取新版本
  。触发实现见 `service_wifi_sync_now()`。
- **轮询仍为默认后台同步行为**，SYNC_NOW 仅为附加的即时触发方式，不改变、不停用
  轮询。
- **不使用 MQTT 长连接**实现同步触发；SYNC_NOW 只是同步触发一次现有
  的一次性拉取流程，用完即释放，不建立任何长连接。
- Ack 经统一帧构造器序列化后 Notify，长度恒等于真实载荷。

> opcode 说明：设计/任务文本记为「(0x32)」仅为**标称值**；`0x32` 在上游基线已是
> `设置 SSID` 命令（见 §4.1），不可复用。故 SYNC_NOW 选取 `0x43` 之后的下一个空闲
> opcode `0x44`，为专用且与既有命令无冲突。

### 4.6 清空全部 `.film`（`0x45`）

| opcode | 命令 | 载荷 / 说明 |
| --- | --- | --- |
| `0x45` | 清空存储中的全部 `.film` | 请求无载荷；响应 1 字节 = 实际删除的文件数（失败 `0xFF`）|

用途：**只保留当天菜单**。发送方在下发新一套画面【之前】调用一次，避免历史版本的图片
（甚至上一版固件时代传入的图）留在存储里被按键轮播翻出来。

行为约定：

- **不清屏**：当前画面保留到下一张图上屏，避免清空瞬间白屏。
- **传输进行中会被拒绝**（文件事务处于 `FT_RECEIVING`/`FT_VALIDATING` 时返回 `0xFF`，
  且不删除任何文件）。应当先清空再开始传输，不要边传边清。
- 清空后刷新文件列表并把轮播游标复位到 0。
- 实现见 `service_file_clear_all()`。

> 轮播顺序：文件列表按**文件名升序**排序（`file_list_refresh_event`），因此下发多张时
> 用序号前缀命名（`1_today.film` / `2_breakfast.film` / `3_lunch.film` / `4_dinner.film`）
> 即可得到确定的翻页次序。早期版本按 `readdir` 原始顺序，次序不可预期。

### 4.7 静默接收（`0x46`）

| opcode | 命令 | 载荷 / 说明 |
| --- | --- | --- |
| `0x46` | 设置静默接收模式 | 1 字节 `0`=关闭 / 非 0=开启；响应 1 字节当前状态 |

开启后，接收完成（`FILE_STOP` 提交成功）**只保存文件并刷新列表，不触发上屏**。

**连发多张时必须使用。** 电子纸刷一次约 **20 秒**（实测 `Loaded file` 到
`Refresh event completed` 间隔），期间设备忙于送屏。而固件在每次 `FILE_STOP` 成功后会
**同步**触发显示，因此连发 N 张会刷 N 次屏；对端在等待中极易 GATT 超时断连——现象就是
「单张可以传，连发四张必失败」，报 `GATT operation failed for unknown reason` 后断开。

正确用法：

```
0x46 (1)  开启静默
传第 1..N-1 张   （只保存，不刷屏）
0x46 (0)  关闭静默
传第 N 张（今日总览）→ 自动上屏，成为默认画面
```

约束：

- **不持久化**：重启后回到 0（正常上屏），避免异常中断后设备永久不刷新。
- **断连自动复位**：`ble_film_trans_abort_on_disconnect()` 会把静默复位为 0。否则
  「开启静默后中途断开」将导致设备此后收到任何图都不上屏，且无任何界面提示，只能重启恢复。
- 缺载荷时按「开启」处理（发送方意图显然是要静默），避免因少一字节退化成逐张刷屏。

### 4.8 设备图片管理（既有 `0x05` / `0x06` / `0x07`）

| opcode | 命令 | 载荷 / 响应 |
| --- | --- | --- |
| `0x06` | 查询文件列表 | 请求无载荷；**每个文件回一帧** `[id][name_len][name...]`，最后回 `[0xFF][0x00]` |
| `0x07` | 显示指定 id | 1 字节 file id |
| `0x05` | 删除指定 id | 1 字节 file id |
| `0x45` | 清空全部 | 见 §4.6 |

注意：

- 新固件用 `[0xFF][0x00]` 明确结束，调用方可区分空列表与无响应；兼容旧固件时可在至少
  收到一个条目后用静默期判定接收完毕。旧固件在设备没有文件时不会通知，因此只能按
  查询失败处理。
- `name_len = strlen + 1`（含结尾 NUL），解码时要去掉尾部 NUL。
- **删除后 id 会重排**（id 就是排序后列表的下标），删完必须重新查询列表再操作，
  不能沿用旧 id。
- 显示指定 id 会立即刷屏（约 20 秒）。

### 4.9 按当前时段显示（`0x47`）

| opcode | 命令 | 载荷 / 说明 |
| --- | --- | --- |
| `0x47` | 按当前做饭时段显示 | 请求无载荷；响应 1 字节 = 命中的文件索引（失败 `0xFF`）|

设备按本地时间选择要显示的那一张：

```
06:00–09:00  -> 文件名含 breakfast   （做饭窗口内：这一餐的详细做法）
11:00–13:30  -> 文件名含 lunch
17:00–19:30  -> 文件名含 dinner
其余时间      -> 文件名含 today       （窗口外：今日总览）
```

设计取舍：**做饭窗口之外显示总览**，而不是把一天三等分。详细做法（食材/步骤）只在准备
这一餐时有用，平时冰箱贴上更该是今日总览。窗口略宽于实际做饭时刻，留出提前备料看菜谱的时间。

两条触发路径：

1. 整套下发完毕后由发送方发一次 `0x47`（中午下发即直接显示午餐详情）。
2. 固件每分钟自检一次，**仅在应展示类别变化时**切换（`service_film_auto_display_tick()`
   由低功耗管理器提供节拍）。电子纸刷一次约 20 秒且耗电，所以一天最多切 6 次
   （3 次进窗口 + 3 次出窗口），不会反复刷屏。

约束与回落：

- **时间不可信时绝不猜时段**：时间来自 Wi-Fi 同步中的 SNTP，未配网 / 未同步 / 冷启动仍是
  1970 时，`0x47` 直接回落显示今日总览，定时切换完全不触发。
- 时区固定 `CST-8`（`sys_cfg.h` 的 `SFM_LOCAL_TZ`），在 SNTP 成功后 `setenv`+`tzset`。
  SNTP 给的是 UTC，不设时区会偏 8 小时。
- 匹配用**文件名包含**关键字，而非全等——发送方会加序号前缀（`2_breakfast.film`）来固定
  轮播次序，前缀不参与匹配。
- 找不到对应餐段则回落总览；连总览也没有则显示列表第一张，保证有画面。
- **按键手动翻页优先**：手动翻页后 30 分钟内不自动切换，避免打断用户并省掉一次无谓刷屏。
- 时段边界定义在 `service_film.c`（`FILM_*_START_MIN` / `FILM_*_END_MIN`），
  调整用餐时间只需改固件常量，后端与 App 无需改动。

> 文件命名约定（`1_today` / `2_breakfast` / `3_lunch` / `4_dinner`）见
> [docs/contracts/README.md](../../../docs/contracts/README.md)，云端与 App 下发时必须遵守：
> 序号前缀决定翻页次序，餐段关键字决定自动显示。

### 4.10 休眠开关（既有 `0x25` / `0x26`）

| opcode | 命令 | 载荷 |
| --- | --- | --- |
| `0x25` | 休眠模式开关设置 | 1 字节 `0`=关闭 / `1`=开启 |
| `0x26` | 休眠模式开关查询 | 响应 1 字节当前状态 |

**注意 `0x20` 是 film 播放模式，与休眠无关**（早期文档曾误写为用 `0x20` 关休眠）。

`sleep_mode` **持久化在 NVS**，固件里改默认值只对首次启动 / 恢复出厂生效——
**已烧录过的设备仍是旧值**。因此让已有设备进入省电模式必须显式发一次 `0x25=1`。

关联耗电行为：关闭休眠时 CPU 与 BLE 广播 7×24 全开，实测一夜即可把电池耗尽到欠压反复
重启（`BROWNOUT_RST` boot loop，固件起不来、也扫不到设备）。长时间调试可临时 `0x25=0`，
用完记得改回 `1`。

### 4.11 唤醒时间表与轮询周期（`0x48`–`0x4B`）

设备靠电池供电，唤醒一次要做「连 Wi-Fi → TLS 握手 → 拉 manifest → 可能下载 4×209120
字节 → 刷屏」，成本很高，不能按固定短周期猛醒。但冰箱贴的价值恰恰在**饭点前那半小时**。
所以唤醒策略是两条承诺的合成：**饭点前必醒一次** + **最长 N 分钟必醒一次**（兜底，
让非饭点时段手动发布的新画面也能上屏）。饭点由 App 按后端的用餐时间写入。

| opcode | 命令 | 方向 | 载荷布局 | Ack / 响应 |
| --- | --- | --- | --- | --- |
| `0x48` | 设置唤醒时间表 | App → 设备 | `[count][slot0_hi][slot0_lo]…[slotN_hi][slotN_lo][fallback_hi][fallback_lo]`，长度恒为 `1 + 2*count + 2` | 1 字节：`1` 成功 / `0xFF` 拒绝 |
| `0x49` | 查询唤醒时间表 | App → 设备 | 请求无载荷 | 与 `0x48` **完全相同**的布局（可原样再发回） |
| `0x4A` | 设置轮询周期 | App → 设备 | 4 字节大端秒数 | 4 字节大端**钳制后**的实际生效值；长度非法时回 1 字节 `0xFF` |
| `0x4B` | 查询轮询周期 | App → 设备 | 请求无载荷 | 4 字节大端秒数 |

字段语义：
- `slot`：**当地时间的分钟数**（`hour*60+min`），大端 uint16，合法域 `[0, 1439]`。
- `count`：≤ 6（`WAKE_SCHEDULE_MAX_SLOTS`）。上限取 6 是因为三餐各一个唤醒点已覆盖主
  场景，留一倍余量给「早餐前 + 早餐时」这类成对配置；每多一个点就是每天多一次完整联网。
- `fallback`：兜底唤醒周期（**分钟**），`0` = 不启用兜底，上界 `1440*7`（7 天）。
  出厂默认 **1440（24 小时）**。

注意事项：
- **校验失败整条拒绝，绝不部分写入**。任一 `slot ≥ 1440`、`count > 6`、`fallback > 10080`，
  或长度与 `count` 不自洽（多一字节少一字节都算），都直接回 `0xFF` 且设备参数不变。
  半张时间表会让设备在一部分饭点醒、另一部分不醒，而 App 那边显示的是完整配置——
  两边不一致却没有任何一处报错。
- 出厂提供 07:05、11:35、18:05 三个回落槽位。App 根据家庭餐次与提前量整表覆盖，
  不把出厂时间复制为业务常量。
- **两者取较小值**。设备算「距下一个 slot 的分钟数」与 `fallback` 取 min，因此两条承诺
  同时成立。`slot` 恰等于当前分钟时按「明天同一时刻」算（本次唤醒就是为它而来，
  装 0 会让设备在同一分钟里反复睡醒）。装载的秒数下限钳到 60 秒。
- **时间不可信时时间表不生效**。时间来自 Wi-Fi 同步中的 SNTP；冷启动仍是 1970 时，
  由它算出的「距下一个饭点」是错的，设备会醒在毫无意义的时刻。此时回落到
  `fallback`（分钟），`fallback=0` 时才回落到轮询周期。判据与 `0x47` 按时段选图同源。
- **`0x4A` 的 Ack 回的是钳制后的值**（合法区间 `[30, 86400]` 秒）。不回钳制后的值会让
  App 显示 5 秒、设备实际 30 秒，现场调续航时得出错误结论。
- 时间表**持久化在 NVS**，与 `sleep_mode` 一样，改固件默认值只对首次启动 / 恢复出厂生效。
- 当前 `config_version` 为 6。v2-v5 记录按已知布局迁移；SSID、两类密文、
  `manifest_url`、`device_id`、轮询周期、唤醒表和 `last_applied_version` 均保留。
  只有未知版本或损坏记录才回落默认值。

### 4.12 置顶自定义画面（`0x4C` / `0x4D`）

手绘涂鸦与相册照片本身**不需要新协议**：App 把图交给后端渲染成 209120 字节的 `.film`，
再走既有的 `0x03/0x00/0x01/0x02/0x04` 序列传进设备，`FILE_STOP` 成功后自动上屏。

要新协议的是**让它留在屏幕上**。设备默认 10 分钟深睡一次，`service_film.c` 里
「上次自动切换到哪个时段」的状态是普通 `static`（本项目没有任何 `RTC_DATA_ATTR`），
深睡唤醒后归零；时间一同步，第一次 `service_film_auto_display_tick()` 就调
`service_film_display_for_now()` 把自定义图换成菜单。用户看到的是「照片自己没了」。
所以「持续显示」必须靠一份**持久化的 pin**：一个文件名 + 一个模式（+ 可选窗口）。

| opcode | 命令 | 方向 | 载荷布局 | Ack / 响应 |
| --- | --- | --- | --- | --- |
| `0x4C` | 设置置顶画面 | App → 设备 | `[mode][start_hi][start_lo][end_hi][end_lo][name_len][name…]`，长度恒为 `6 + name_len`；`mode == 0`（取消）时**允许只发 1 字节** | 1 字节：`1` 成功 / `0xFF` 拒绝 |
| `0x4D` | 查询置顶画面 | App → 设备 | 请求无载荷 | 与 `0x4C` **完全相同**的布局（可原样再发回）|

三种模式的语义：

| `mode` | 名称 | 行为 |
| --- | --- | --- |
| `0` | OFF | 不 pin。选图行为与没有本功能时**完全一致**。发这个值等于**擦掉整条记录** |
| `1` | ALWAYS | 一直显示自定义图（取缔菜单）。**不依赖时间**，未配网也能用；`auto_display_tick()` 直接返回，一天连一次刷屏都没有 |
| `2` | WINDOW | 只在 `[start, end)` 显示自定义图，其余时间按菜单逻辑 |
| `3` | OUTSIDE_MEAL | 做饭窗口内（§4.9 的三段）显示菜单，窗口外显示自定义图 |

字段语义：

- `start` / `end`：**当地时间的分钟数**（`hour*60+min`），大端 uint16，合法域 `[0, 1439]`，
  仅 `WINDOW` 使用。**支持跨零点**：`start > end` 表示跨午夜，`22:00–06:00` 就写
  `start=1320, end=360`（典型用法：夜里显示照片、白天显示菜单）。
  `start == end` 是**空窗口**（恒不显示）——`[x, x)` 只有零长度这一种自洽读法；
  想表达「全天」请用 `ALWAYS`。
- `name`：pinned 文件的**安全基名**，不带结尾 `\0`（由固件自己补），有效长度 `1..31`。

时间不可信时的行为（时间来自 Wi-Fi 同步中的 SNTP，冷启动仍是 1970 就算不可信）：

| `mode` | 时间不可信时 | 为什么 |
| --- | --- | --- |
| `ALWAYS` | **显示** pinned | 这正是它的价值：没配网也能一直显示照片 |
| `WINDOW` | **不显示** pinned | 绝不猜时段。判据与 §4.9 的 `0x47`、§4.11 的唤醒时间表**同源**——三处不会出现一个信一个不信 |
| `OUTSIDE_MEAL` | **显示** pinned | 不知道现在几点就不可能在做饭窗口里，于是落到 pinned 一侧。**刻意的取舍**：显示用户自己选的照片，比显示一张标着「今日」却可能是昨天的总览更诚实——后者是会误导人的错误信息 |

⚠️ **文件名不得含 `today` / `breakfast` / `lunch` / `dinner` 任一关键字**，固件会直接回
`0xFF`。菜单选图用的是 `strstr` **包含**匹配（因为发送方会加序号前缀，见 §4.9），
所以一张 `my_lunch.film` 会同时被当成「午餐详情页」：中午它作为菜单被选中、窗口外它作为
pinned 被选中，两条路径抢同一个文件。这一条必须由固件拒绝而不是靠 App 自律——症状
（「照片有时会在中午自己冒出来」）离成因太远。

其余拒绝规则（`0xFF`，且设备配置**一个字节都不变**）：

- `mode > 3`；
- `start` 或 `end` `≥ 1440`（即便当前 mode 用不到窗口也校验：记录会被 `0x4D` 回读、
  被 App 原样发回，非法值留在记录里迟早会生效）；
- 长度与 `name_len` 不自洽（多一字节少一字节都算）；
- `name_len == 0` 或 `≥ 32`；
- 文件名含 `[0-9A-Za-z._-]` 之外的字符（空格、`/`、`\`、通配符、非 ASCII 全部拒绝）、
  是 `.` 或 `..`、任意位置含 `..`；
- 不以 `.film` 结尾，或只有 `.film` 而没有基名。

**校验失败整条拒绝，绝不部分写入**（与 `0x48` 同一约定，理由相同）：半份配置会让设备
在一部分时间显示对、另一部分显示错，而 App 显示的是完整配置，两边不一致却没有任何一处报错。

pin 只影响**自动选图**，不锁屏：

- 生效点只有两处：`service_film_display_for_now()`（`0x47` / FN 短按 / Wi-Fi 整套下载成功
  后的选图都汇到这里）与 `service_film_auto_display_tick()`（定时自检）。
- **`0x07` 指定显示、侧边键翻页完全不受 pin 影响**。否则用户传了新图看不到、也不能临时
  翻页看菜单。pin 的语义是「自动选图时优先它」，不是「锁死屏幕」。
- pinned 文件**不在设备上了**（用户删了 / 被 `0x45` 清空 / 名字改了）：记一条
  `pin display: pinned file '…' not found` 的 warning 并**继续走菜单逻辑**，绝不空屏。
  这条 warning 是现场唯一能解释「pin 配了却不生效」的线索。
- `WINDOW` / `OUTSIDE_MEAL` 支持**双向**切换：进窗口切到 pinned、出窗口切回菜单
  （自动切换的目标是 `(餐段, 是否 pinned)` 两维，所以窗口在同一餐段中途开始/结束时也能切）。

✅ **本次改动不会丢配网。** pin 配置存在 `SFM_NVS` 下一个**独立的 blob key（`PINNED`）**，
`PARAMS` blob 的长度保持 **923** 字节，当前 `config_version` 为 **6**。pin 不占
`ServiceParam_Def_t`，因此升级 pin 功能不会触发主参数迁移或清空配网。pin 记录自带
magic + version + body_len，**记录不存在 / 长度不符 / 内容非法都
一律视为「未 pin」**（回落到原有菜单行为），绝不因此重置别的东西。
恢复出厂（`0x22`）会一并擦掉这条记录——否则恢复出厂后设备还挂着上一位用户的照片，
而用户以为已经清干净了；用户存储上的 `.film` 文件仍然不动。

> 文件命名约定：自定义图用 `photo_*.film`（相册照片）/ `draw_*.film`（手绘涂鸦），
> 见 [docs/contracts/README.md](../../../docs/contracts/README.md)。

### 4.13 遗留取图路径的停用（`0x36` / `0x37` / `0x3C` / `0x3D`）

上游固件有**两条** Wi-Fi 取图链路，安全等级差距悬殊，而松的那条是自动触发的：

| | manifest 同步路径 | 遗留 PSRAM 下载路径（已删除）|
| --- | --- | --- |
| 地址来源 | `manifest_url`（`0x3E`），**强制 https 校验** | `film_api_url`（`0x36`），**无 scheme 校验** |
| TLS | `HTTP_TRANSPORT_OVER_SSL` + `esp_crt_bundle` | 只填 url/handler/timeout ——**http 就走明文** |
| 鉴权 | `Authorization: Bearer {device_token}` | **无** |
| 完整性 | manifest SHA-256 + 原子替换 | 仅 209120 字节长度上限，**无摘要校验** |
| 落盘 | 流式写入文件事务 | 整份 realloc 进 PSRAM 再写 |
| 触发 | 轮询 / `0x44` / 唤醒 | **Wi-Fi 播放模式下一联网就自动跑** |

也就是说「固件强制 HTTPS」此前**并不成立**：严的那条管住 manifest 同步，松的那条会在每次
联网时自行启动，且因为没有摘要校验，中间人可把画面替换成任意内容。故做如下调整：

| opcode | 变更 | 现行为 |
| --- | --- | --- |
| `0x36` | 停用写入 | 忽略并告警。它是遗留路径唯一的输入口，留着等于保留「把设备指向任意明文地址」的开关，而已无任何读取方 —— 写进去只会造成「配了却不生效」的困惑。改用 `0x3E` |
| `0x37` | 停用查询 | 恒返回**空串**。返回残留旧值会误导（上位机看到配着地址、设备却从别处取图）。改用 `0x3F` |
| `0x3C` | 转为别名 | 等价于 `0x44` SYNC_NOW，保留仅为不破坏已有上位机 |
| `0x3D` | 语义收窄 | 状态只有 `IDLE` / `DOWNLOADING`（由同步任务忙标志派生）；不再有 `DONE` / `ERROR` —— 失败原因改由 `0x43` 状态查询里的 `last_sync_error` 提供，比笼统的 ERROR 有用。进度字段流式路径不跟踪字节级进度，忙时报 `0`、空闲报 `100`，判据以状态字节为准 |

`network.film_api_url` 字段本身**保留不删**：它在参数序列化里占 128 字节定长槽位，
删除会改变 NVS blob 布局并需要 `config_version` 迁移 —— 为一个不再读取的字段去动持久化
布局，风险大于收益。恢复出厂仍会清空它。

## 5. 兼容性与边界

- 保留 FrameFilm 公开 BLE UUID、FILE_* 命令序列与全部既有 opcode 取值/语义。
  例外：`0x36`/`0x37` 已停用、`0x3C`/`0x3D` 语义调整，原因见 §4.13（安全等级不一致，
  且取值本身未变，旧上位机不会收到未知 opcode 错误）。
- 追加的 opcode `0x3E–0x4D` 连续排布（`0x3E–0x43` 配网/状态查询 + `0x44` SYNC_NOW +
  `0x45`–`0x47` 文件管理/按时段显示 + `0x48`–`0x4B` 唤醒时间表与轮询周期 +
  `0x4C`–`0x4D` 置顶自定义画面），未与既有命令冲突。当前已用 opcode 范围
  `0x00`–`0x4D`，下一个空闲值是 `0x4E`。
- **两次持久化改动的区别值得记住**：`0x48`（唤醒时间表）扩展了 `ServiceParam_Def_t`，
  记录长度一变 `nvs_init()` 就整份重置，**升级丢配网**；`0x4C`（置顶画面）走的是同
  namespace 下的**独立 blob key**，`PARAMS` 布局与 `config_version` 都没动，
  **升级不丢配网**。后加持久化字段时优先照 `0x4C` 的做法。
- 不新增第二套 BLE 数据格式；Android 兜底传图仍走既有 `.film` 分片流程。
- 自定义控制特征和通知描述符要求加密链路；Android 在连接 GATT 前完成 Secure Connections
  bonding。设备采用 NoInputNoOutput 配对，可防被动嗅探和未配对写入，但不提供物理 MITM
  防护。敏感字段同时保留「at-rest 加密 + 禁止读回 + 日志脱敏」。
- 恢复出厂会清除固件侧 bond；手机系统中保留的旧配对也应由用户删除后再重新配网。
